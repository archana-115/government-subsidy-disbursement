Project Overview The Digital Subsidy and Grant Administration Platform is a full-stack web application for managing the end-to-end lifecycle of government subsidy programs — from beneficiary application submission through officer verification, admin approval, officer allocation, field inspection, and milestone-based fund disbursement. Purpose of the Frontend The frontend is a single-page application (SPA) that serves as the interface layer for four distinct user roles — Beneficiary, Officer, Finance Officer, and Admin — each with a separate dashboard and workflow. It handles form-based data entry, real-time status tracking, document and media uploads, and analytics visualization, while delegating all business logic, persistence, and authentication decisions to the backend. Role of the Frontend in the Overall System The frontend communicates exclusively with the Spring Boot backend via a REST API (JSON) over HTTP, using a single shared Axios client. Authentication state is maintained via an HttpOnly cookie issued by the backend; the frontend does not independently manage or store a JWT token. Main Technologies / Frameworks Used ● React 19 (via Vite) — core UI library and build tooling ● React Router v7 — client-side routing ● Axios — REST API communication ● Recharts — dashboards and analytics visualization ● Framer Motion — animation and page transitions

Frontend Architecture The frontend follows a flat, page-centric architecture rather than a deeply layered one. State Management Local State The application relies entirely on React's built-in useState/useEffect hooks at the component level. Every page manages its own loading, error, form, and fetched-data state independently -- there is no shared or lifted state between pages. Two mechanisms exist that approximate global concerns, both narrow in scope: ● ThemeContext (src/context/ThemeContext.jsx): A React Context wrapping the entire app via ThemeProvider in App.jsx. However, it is non-functional as a theme switcher -- theme is hardcoded to 'light', toggleTheme is a no-op function, and the useEffect unconditionally sets data-theme="light" on the document root regardless of any state change. It provides the shape of a theming system without an actual dark-mode implementation. ● sessionCleanup.js: Not state management per se, but a shared side-effect utility (clearPortalSessionCaches()) that clears a fixed list of localStorage/sessionStorage keys on logout or session-expiry, called from multiple pages and from the api.js interceptor. Custom Hooks One custom hook exists -- useDashboardAnalytics (src/hooks/useDashboardAnalytics.js). It encapsulates a Promise.all of nine dashboard API calls, response unwrapping, and data reshaping into chart-ready arrays, returning { data, loading, error } to the consuming component (scheme-dashboard.jsx). Data Flow Strictly top-down and page-local -- a page fetches its own data on mount via useEffect, stores it in useState, and passes it down to child components (ProfilePanel, AdminLayout, DashboardTopbar) as props. There is no prop-drilling of significant depth, since the shared components are shallow (page to component, not page to component to sub-component). Persistence Mechanisms Session/auth state is not persisted client-side beyond the browser's own handling of the HttpOnly cookie (see Section 11). sessionCleanup.js references four localStorage/sessionStorage cache keys (gov￾subsidy-applications, gov-subsidy-officer-applications, gov-subsidy-finance-audit-logs, gov-subsidy-auth) <PARSED TEXT FOR PAGE: 13 / 22> Digital Subsidy and Grant Administration Platform — Frontend Technical Documentation Page 13 of 22 that are cleared on logout, implying some pages may cache fetched data under these keys for the session.
API Integration API Client A single shared Axios instance, defined in src/services/api.js. Authentication & Authorization Login Flow User submits credentials via Login.jsx -> authService.login() -> POST /gov/auth/signin. On success, the backend sets an HttpOnly token cookie. The frontend then makes a separate GET /gov/auth/profile/get call to retrieve the user's role, since the sign-in response does not include it, and redirects based on that role. Registration Flow Two entry points -- Register.jsx (dual-mode tab switcher for Beneficiary/Officer) and a standalone OfficerRegister.jsx. Both call POST /gov/auth/signup with a role field. Officer accounts require a separate Admin approval step (via adminService.updateApprovalStatus()) before they can log in -- stated explicitly in the Register UI copy and reflected in a dedicated officer-approval endpoint and Admin Dashboard section. <PARSED TEXT FOR PAGE: 15 / 22> Digital Subsidy and Grant Administration Platform — Frontend Technical Documentation Page 15 of 22 Token / Session Handling JWT is issued and validated entirely server-side; the frontend has no code path that reads, stores, or manually attaches the token. This is a more secure pattern than typical localStorage-JWT setups, but it does mean the frontend cannot proactively detect an expired session before making a request -- it only learns of expiry when a request returns 401. Storage Mechanism No client-side token storage. sessionCleanup.js manages cache data (not the token itself) in localStorage/sessionStorage, cleared on logout or session-expiry. Logout Each dashboard page independently calls POST /gov/auth/signout directly via the shared api instance (not via a dedicated authService function), then calls clearPortalSessionCaches() and navigates to /login or /. Role-Based UI Behavior Roles (ADMIN, FINANCE_OFFICER, FIELD_OFFICER, DISTRICT_OFFICER, REGIONAL_OFFICER, BENEFICIARY) determine which dashboard a user lands on post-login, and ProfilePanel's ROLE_LABELS mapping adjusts display text per role. UI / Styling Architecture CSS Approach Plain CSS files (no CSS-in-JS, no Tailwind, no CSS Modules) using CSS custom properties (design tokens) defined in :root. Theme System A ThemeContext exists structurally but is non-functional -- hardcoded to a single light theme with a no￾op toggle (see Section 9). A Real Inconsistency Worth Flagging Two separate global stylesheets define two different, non-overlapping design-token systems: ● index.css -- a light, government-portal palette (--brand-green: #087443, white backgrounds, Inter/Source Serif 4 fonts). ● App.css -- a dark palette (--bg: #07130f, near-black backgrounds, amber/gold accents, Noto Sans/Source Serif 4 fonts). Individual page stylesheets reference variables from one or the other set depending on which page they style -- so which "theme" a given page visually follows depends on which token set its CSS file happens to reference, not on any runtime theme logic. Error Handling API Failures Centralized in the api.js response interceptor (see Section 10). All rejected promises carry a normalized Error with a human-readable .message, extracted from the backend's error response body where available. Individual pages catch this in their own try/catch blocks and display it via a local error state string. Validation Failures Handled entirely client-side before any API call is made, via the manual validate() functions described in Section 12. Errors are shown inline, not as toasts, except in Register.jsx which uses a toast only for the success case. Unauthorized Requests (401) Handled globally by the api.js interceptor -- clears session caches (clearPortalSessionCaches()) and redirects to /login, with a guard flag (redirectingToLogin) to prevent multiple simultaneous redirects if several requests fail at once. Explicitly bypassed for the two auth endpoints themselves (/gov/auth/signin, /gov/auth/signup) and when already on a login/register page, so a failed login attempt shows its own error message instead of forcing a redirect loop. Loading States Handled per-page via a local loading boolean, typically shown as a spinner or a disabled submit button during in-flight requests. useDashboardAnalytics exposes its own loading flag for the analytics dashboard. Network Errors (Backend Unreachable) Login.jsx's catch block includes an explicit fallback message -- "Server is down or unavailable" -- for errors that don't match its known error-string patterns. Frontend Maintenance Guide Add a New Page ● Create the .jsx file under the appropriate src/pages/ subfolder (or a new one, following the existing admins/ / auth/ / beneficiary/ / officers/ grouping). ● Add a corresponding  entry in App.jsx (project root). ● If the page needs a shared header/shell, use DashboardTopbar or AdminLayout rather than building a new one. Add a New Component ● Only extract a new shared component if genuinely reused across 2+ pages -- the existing pattern favors page-local JSX over premature abstraction. ● Place it in src/components/. Add a New API Endpoint Integration ● Add a new exported function to the relevant domain service file (e.g. a new disbursement￾related call goes in fundsService.js), following the existing pattern of a thin async wrapper around api.(). ● If the backend response shape is inconsistent, apply the existing response.data?.data || response.data ||  defensive-unwrap pattern for consistency. Change Navigation ● Route paths are defined only in App.jsx -- this is the single place to add, remove, or rename routes. ● Redirect logic embedded in components (e.g. Login.jsx's role-based redirect) must be updated separately if role names or target routes change -- there is no central route-mapping config. <PARSED TEXT FOR PAGE: 21 / 22> Digital Subsidy and Grant Administration Platform — Frontend Technical Documentation Page 21 of 22 Change Styling ● Be aware of the two competing global token systems (index.css vs App.css -- see Section 13) before adding new var(--...) references; confirm which token set the target page's stylesheet actually uses. ● Per-page CSS lives in src/styles/, one file per page/feature area -- follow that convention rather than introducing co-located component CSS. Add a New Form ● Follow the existing hand-rolled pattern: a form state object via useState, a dedicated validate() function returning an error string or null, and a local error state for display -- there is no validation library to plug into. Add New Environment Configuration ● There is currently no .env infrastructure to extend. Introducing one would require adding Vite's import.meta.env.VITE_* convention from scratch, updating api.js to read from it instead of the hardcoded baseURL, and creating a .env.example file.
